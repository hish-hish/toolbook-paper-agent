# D5 章节识别：规则优先 + LLM 兜底

> 一句话：章节号先从文档自带的目录/标题里"读"出来（规则）；实在没有，才请 LLM"猜"一个，并明确标注这是系统编号、不是原书章节号。

## 1. 这个决策点解决什么问题？

你的核心承诺是"返回章节号，让用户能翻回原书核对"。那么章节号从哪来？三种来源，可靠性递减：

1. **文档自带目录**（PDF 书签、DOCX 标题样式、EPUB 目录文件）——作者/出版社标的，最可靠。
2. **标题文本里的编号**（如正文写着"3.2.1 傅里叶变换的性质"）——正则就能抓出来。
3. **什么都没有**（无目录、无编号的扫描重排文档）——只能让系统自己编。

## 2. 名词解释

- **规则识别**：用确定性代码（读书签、读样式、正则匹配 `第X章` / `\d+(\.\d+)*`）提取章节，结果可复现、零成本。
- **LLM 兜底**：把文档开头部分喂给大模型，让它提议一份章节树。灵活但可能出错。
- **系统编号**：LLM 兜底或系统自动生成的编号，打上特殊标记，与原书真实章节号区分。

## 3. 为什么选"规则优先 + LLM 兜底"（优势）

| 优势 | 说明 |
|---|---|
| 90%+ 场景走规则 | 教材/论文几乎都有目录或编号，规则覆盖绝大多数，零成本零幻觉 |
| 诚实标注 | 兜底产生的编号标"系统编号"徽标，用户知道这不是原书章节号——**可溯源原则的体现** |
| 全覆盖 | 再烂的文档也有章节结构可用，不会导入失败 |

落选方案：纯规则遇到无目录文档直接失败；纯 LLM 又贵又慢还可能**编造章节号**——对"可溯源"项目是致命伤。

## 4. 在本项目中怎么工作（工作环节）

```
导入文档
  │
  ├─ 有目录/标题样式？ ──是──→ 直接建章节树（来源=原书）
  │
  ├─ 标题带编号？ ──是──→ 正则提取编号建章节树（来源=原书）
  │
  └─ 都没有 ──→ LLM 读文本提议章节树
                 → 人工可预览确认
                 → 建章节树（来源=系统编号，打徽标）
```

章节树统一格式：`章节号 | 标题 | 层级 | 父章节 | 来源标记 | 原文定位`，存入 SQLite（D13）。后续检索结果沿章节树回溯出处时，来源标记一路透传到 UI（D12）。

## 5. 初学者常见问题

- **Q：LLM 兜底会不会把章节编错？**
  A：会，所以它只是"兜底"且明确标注。UI 上用户能看到"系统编号"徽标，知道要谨慎对照。
- **Q：章节号重复怎么办（两本书都有第3章）？**
  A：章节号永远和文档绑定，出处格式是"《书名》第3章 3.2节"，不会跨书混淆。
