# D1 编排框架：LangGraph

> 一句话：LangGraph 是整个 Agent 的"流程调度员"，决定先做什么、后做什么、核验不通过时回头重做哪一步。

## 1. 这个决策点解决什么问题？

你的 Agent 不是"问一句答一句"的聊天机器人，而是一条**多步骤流水线**：

```
理解问题 → 检索资源库 → 精挑结果 → 核对原文 → 组织答案
```

其中还有"回头路"：核对原文发现对不上，要**回去重新检索**。谁来管理这条流水线的顺序、分支和循环？这就是编排框架的工作。

## 2. LangGraph 是什么（大白话）

把流程画成一张**地铁线路图**：

- **节点（Node）** = 地铁站 = 一个步骤（如"检索""核验"）。
- **边（Edge）** = 轨道 = 步骤之间的走向，可以带条件（"核验通过走这边，不通过走那边"）。
- **状态（State）** = 一张随车携带的"任务单"，记录当前问题、检索到的片段、核验结果等。每经过一站，任务单被更新，下一站能看到前面所有站留下的信息。

LangGraph 是 LangChain 团队出的框架，专门用这种"图"的方式写 LLM 应用流程。

## 3. 为什么选它（优势）

| 优势 | 对本项目的意义 |
|---|---|
| 天然支持**循环和条件分支** | "核验不通过 → 重新检索（最多 2 次）"这条回头路，用一条带条件的边就能表达 |
| **状态可持久化** | 模块B"解析完论文后等待用户提问"，会话状态可以存下来，用户隔一会儿再问也不丢上下文 |
| 每一步都是显式函数 | 出问题能精确定位是哪一站，调试不黑盒；比赛答辩时流程图直接就是架构图 |
| 与 LangChain 生态兼容 | 需要现成组件（如文档加载器）时可以随手借用 |

对比落选方案：LangChain 的"链"是直来直去的流水线，画回头路很别扭；LlamaIndex 检索强但流程编排弱；纯手写透明但循环/状态管理全要自己造轮子，12 天工期不划算。

## 4. 在本项目中怎么工作（工作环节）

**模块A 查询流程图：**

```
[接收问题] → [查询改写] → [混合检索] → [重排序] → [原文核验]
                 ↑                                    │
                 └──── 不通过且重试<2次 ──────────────┤
                                                      │通过
                                                [生成答案+出处] → [返回]
```

各环节职责：
1. **接收问题**：拿到用户输入，初始化 State（任务单）。
2. **查询改写**：LLM 把问题改写成更适合检索的形式（含中英双语关键词，见 D7 文档）。
3. **混合检索**：BM25 + 向量两路查，RRF 合并（D7）。
4. **重排序**：reranker 精挑 top-5（D10）。
5. **原文核验**：两级核验（D11）。不通过 → 沿回头路换个查询词重查；重试超限 → 走拒答路径。
6. **生成答案**：LLM 基于核验过的内容写答案，强制附引用。

**模块B** 多两个前置节点：`[解析论文PDF] → [展示论文目录，等待提问]`，之后进入同一条查询流程，只是查询改写时会带上论文上下文。

## 5. 初学者常见问题

- **Q：LangGraph 和 LangChain 要一起学吗？**
  A：本项目主要用 LangGraph 的图 API，LangChain 只按需借个别组件，不必系统学。
- **Q：State 里放什么？**
  A：问题原文、改写后的查询、检索结果列表、核验结论、重试次数、最终答案。就是一个 Python 字典/数据类。
- **Q：会不会很难？**
  A：核心概念只有"节点、边、状态"三个，本项目的图总共不到 10 个节点，一天能上手。
