# D13 元数据存储：SQLite

> 一句话：SQLite 是一个"装进单个文件的数据库"——Python 自带、零安装，用来存书籍信息、章节树和原文，是整个系统的"账本"。

## 1. 这个决策点解决什么问题？

系统里有一大堆**结构化信息**要持久保存、快速查询：

- 导入了哪些书？每本书的章节树长什么样？
- 3.2 节的原文全文是什么？在第几页？
- 某个检索命中的子块属于哪个父块、哪一章？

这些信息要支持"按章节号直查""按父块ID取原文""按文档删除重建"等操作。放内存里一关机就没了，放 JSON 文件里查询要全量加载、容易乱——需要一个真正的数据库。

## 2. SQLite 是什么（大白话）

- **单文件数据库**：整个数据库就是项目目录里的一个 `library.db` 文件，拷走它=拷走全部书籍账本。
- **零部署**：不用安装、不用起服务，Python 标准库自带 `sqlite3`，开箱即用。
- **会 SQL**：支持标准查询语言，"给我《信号与系统》第3章下所有小节"就是一句 SELECT。
- **事务安全**：导入中途崩溃不会留下半本书的脏数据。

## 3. 为什么选它（优势）

| 优势 | 说明 |
|---|---|
| 零依赖零部署 | 与 Chroma 一起构成"双击就能跑"的单机系统 |
| 树状章节查询天然合适 | 章节树用"父章节ID"字段表达，一句 SQL 查整棵子树 |
| 规模舒适区 | 3 本书的数据量对 SQLite 是毛毛雨（它撑到 GB 级都没问题） |
| 与 Chroma 分工清晰 | SQLite 存原文+结构，Chroma 存向量，ID 关联，各展所长 |

落选方案：JSON 文件无事务、查询低效、文档多了难维护。

## 4. 在本项目中怎么工作（工作环节）

**三张核心表（初步设计）：**

```
documents 书籍表
  doc_id | 书名 | 格式 | 文件哈希 | 导入时间

sections 章节表（章节树）
  section_id | doc_id | 章节号 | 标题 | 层级 | 父section_id
             | 来源标记(原书/系统编号) | 原文全文 | 页码/段落定位

chunks 子块表
  chunk_id | section_id(父块) | 子块文本 | 序号
```

**各环节怎么用：**
1. **导入**（D3–D6）：解析结果写入三张表；文件哈希查重，重复导入直接跳过。
2. **章节号直查**：`SELECT 原文 FROM sections WHERE doc_id=? AND 章节号=?`。
3. **检索回查**（D7）：Chroma 返回 chunk_id → 查 chunks 得 section_id → 查 sections 得整节原文+出处。
4. **核验**（D11）：机械匹配用的原文就从 sections 表取。
5. **删除重建**：按 doc_id 级联删三张表 + Chroma 对应向量。

## 5. 初学者常见问题

- **Q：要学 SQL 吗？**
  A：只需会 SELECT/INSERT/DELETE 三件套，半小时入门；也可以用 SQLAlchemy 等工具写 Python 式查询。
- **Q：数据库文件坏了怎么办？**
  A：原始文档还在，重新导入即可重建——账本可再生，这也是导入幂等设计的价值。
