# D6 分块策略：父子块（小块检索 + 大块返回）

> 一句话：把书切成"小卡片"用来搜索，命中后返回卡片所属的"整个小节"用来阅读——搜索要准，阅读要全。

## 1. 这个决策点解决什么问题？

检索系统没法拿整本书去比对，必须先把文本切成片段（**chunk，块**）。切法有个两难：

- **块太大**（整章一块）：一块里混了好几个主题，检索时"稀释"了真正相关的句子，查不准。
- **块太小**（两三句一块）：查得准，但返回给用户的内容没头没尾，读不懂。

## 2. 父子块是什么（大白话）

像图书馆的**索引卡片系统**：

- **子块（小卡片）**：约 200–400 字的一段，只用来**建索引、做检索**。卡片小而主题集中，搜索命中率高。
- **父块（大卡片）**：子块所属的**整个小节**（如完整的 3.2.1 节）。命中任何一张小卡片，就把整张大卡片取出来给用户和 LLM 看。

每个子块都记着"我属于哪个父块、哪个章节、哪本书"，这条链就是出处的来源。

## 3. 为什么选它（优势）

| 优势 | 说明 |
|---|---|
| 精度与上下文兼得 | 小块保检索精度，大块保答案上下文完整，是 RAG 进阶标配（small-to-big） |
| 与章节天然对齐 | 父块=小节，返回内容自带完整章节号，完美服务你的核心需求 |
| 核验更有料 | D11 核对原文时拿整个小节比对，不会因为块太碎而误判"无依据" |

落选方案：固定长度切分会拦腰切断小节；语义分块要额外跑模型且不解决章节对齐。

## 4. 在本项目中怎么工作（工作环节）

**导入时（建索引）：**
1. 沿 D5 的章节树，把每个小节定为**父块**。
2. 小节内按段落/句子边界切成**子块**（目标 200–400 字，不切断句子）。
3. 子块向量化（D8）后存入 Chroma（D9），元数据带 `父块ID/章节号/文档ID`。
4. 父块全文存 SQLite（D13）。

**查询时（用索引）：**
1. 检索命中的是**子块**。
2. 按 `父块ID` 去 SQLite 取**整个小节**。
3. 同一小节命中多个子块时去重，只返回一份父块。
4. 父块进入重排（D10）与核验（D11）。

## 5. 初学者常见问题

- **Q：小节特别长（上万字）怎么办？**
  A：父块设上限（如 2000 字），超长小节再按段落群切成几个父块，仍保持章节号不变。
- **Q：子块切多大合适？**
  A：起步 300 字左右，比赛评测集（计划书 M5）上调参对比，不用拍脑袋。
