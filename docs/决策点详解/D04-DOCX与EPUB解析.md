# D4 DOCX/EPUB 解析：python-docx + ebooklib

> 一句话：Word 和 EPUB 天生自带"章节标记"，用两个轻量标准库直接读出来即可，不需要重型工具。

## 1. 这个决策点解决什么问题？

资源库三种格式中，PDF 是硬骨头（交给 MinerU，见 D3），而 DOCX 和 EPUB 其实**结构信息很干净**：

- **DOCX**：作者写书时用的"标题1/标题2/标题3"样式，就是现成的章节层级标记。
- **EPUB**：本质是一个 zip 压缩包，里面装着 HTML 正文 + 一份官方目录文件（NCX 或 NAV），章节树是标配。

所以这两种格式不需要 AI 模型，用标准库"按标记读取"就行。

## 2. 两个库是什么（大白话）

- **python-docx**：读写 Word 文档的 Python 标准库。把 DOCX 看成"段落列表"，每个段落带着自己的样式名。遍历一遍，遇到样式叫 `Heading 1` 的段落就是章标题，`Heading 2` 就是节标题。
- **ebooklib**：EPUB 解析库。解开 zip，读目录文件拿到章节树，再按顺序读各章 HTML，转成纯文本。

## 3. 为什么选它（优势）

| 优势 | 说明 |
|---|---|
| 章节号几乎零歧义 | 直接来自文档自身的样式/目录，与原书完全一致，可拿实体书对照 |
| 轻量、零模型依赖 | pip 即装，不占显存，导入速度快 |
| 定位信息完整 | DOCX 可记段落序号、EPUB 可记 spine 位置，原文核对（D11）能精确定位 |

落选方案：Pandoc 统一转换会丢定位信息；Unstructured 是黑盒，章节号提取不精细。

**已知边界**：如果作者不用标题样式、纯靠手动加粗字号冒充标题，样式法会漏。兜底：按"字体大小/加粗 + 编号正则（如 `3.2.1 xxx`）"的规则补识别，再不行走 D5 的 LLM 兜底。

## 4. 在本项目中怎么工作（工作环节）

**DOCX 路线：**
1. python-docx 打开文件 → 遍历段落。
2. 按标题样式切分出章节树；正文段落挂到所属章节下。
3. 记录每段的段落序号（用于原文定位）。

**EPUB 路线：**
1. ebooklib 解包 → 读 NCX/NAV 目录 → 得到章节树。
2. 按 spine（阅读顺序）读各章 HTML → 提取纯文本。
3. 记录每章的 spine 位置。

两条路线的产物统一为：**章节树 + 带定位的正文** → 交给 D5 校验编号 → D6 分块 → D13 入库。

## 5. 初学者常见问题

- **Q：为什么不三种格式都用 MinerU/Unstructured 一把梭？**
  A：能用干净结构信号就别用模型猜。样式/目录是作者亲手标注的，比任何模型识别都准，还快。
- **Q：老格式 .doc / .mobi 怎么办？**
  A：一期不支持，提示用户先转成 docx/epub。比赛场景 3 本书，不值得为边缘格式加依赖。
