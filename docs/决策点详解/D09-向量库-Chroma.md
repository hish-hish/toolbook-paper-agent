# D9 向量存储：Chroma

> 一句话：Chroma 是一个"装进口袋的向量仓库"——pip 装完就能用，不用启动任何服务，专门存放向量并支持"找最相近"和"按标签过滤"。

## 1. 这个决策点解决什么问题？

D8 把几千个子块翻译成了向量，这些向量得有个地方存，并且要能极快地回答："给我离这个向量最近的 30 个块"。这就是**向量库**的工作。普通数据库不会算"向量距离"，所以需要专门的库。

## 2. Chroma 是什么（大白话）

- **嵌入式**：像 SQLite 一样，它是你程序里的一个库 + 一个本地文件夹，`pip install chromadb` 就装好了，**不需要 Docker、不需要起服务**。
- **近邻搜索**：内置索引算法，几千到几十万条向量都能毫秒级找出最相近的。
- **元数据过滤**：每条向量可以挂标签（如 `book=《信号与系统》, chapter=3.2`），查询时能说"只在《信号与系统》第3章里找"。

## 3. 为什么选它（优势）

| 优势 | 说明 |
|---|---|
| 零部署 | 单机一键启动，比赛演示不翻车 |
| 元数据过滤 | 直接支持"限定某本书/某章检索"，贴合资源库场景 |
| 规模刚好 | 3 本书 ≈ 几千条向量，Chroma 的舒适区（它的短板是百万级以上，与你无关） |
| 教程多 | 初学者遇到问题好搜 |

落选方案：FAISS 只是索引算法库，存储/元数据/增删都要自己包一层；LanceDB 生态较新中文资料少；Milvus/Qdrant 要起服务，对个人项目过重。

## 4. 在本项目中怎么工作（工作环节）

**存（导入时）：**
```
子块文本 → embedding(D8) → 向量
Chroma.add(
  id = 子块ID,
  embedding = 向量,
  metadata = {文档ID, 章节号, 父块ID, 页码},
)
```

**取（查询时）：**
```
问题向量 → Chroma.query(向量, n_results=30,
             where={"文档ID": ...})   ← 可选：限定某本书
        → 返回最近的子块ID列表
        → 按父块ID去 SQLite(D13) 取整节原文
```

**删（重新导入时）**：按文档ID批量删除旧向量再重建，配合文件哈希去重。

分工记忆：**Chroma 管"向量+标签"，SQLite 管"原文+章节树"**，两边用子块ID/父块ID关联。

## 5. 初学者常见问题

- **Q：数据存在哪？**
  A：项目目录下一个 `chroma_data/` 文件夹，拷走它=拷走整个向量索引。
- **Q：和 SQLite 什么关系？**
  A：互补不重复。Chroma 不擅长存大段原文和树状结构，SQLite 不擅长向量近邻搜索，各干各的强项。
